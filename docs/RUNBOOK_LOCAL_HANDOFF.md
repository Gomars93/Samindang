# 로컬 핸드오프 서버 운영 가이드 (파일럿, 클리닉 LAN 전용)

이 문서는 환자 태블릿에서 작성한 문진이 사람이 직접 옮기지 않고 원장
PC 화면까지 도착하도록 하는 최소 서버(`server/index.js`)의 운영 절차를
설명한다. 데이터 계약은 Master Spec 13장 참고.

**전제**: 인터넷에 노출하지 않는다. 클리닉 원내 LAN(같은 공유기/스위치)
안에서만 동작하는 파일럿 등급 구성이며, 실제 인증/암호화(TLS)를 갖춘
프로덕션 시스템이 아니다.

## 0. 요약 (바쁠 때 여기만)

- **환자 데이터 저장 위치**: `SAMINDANG_DATA_DIR`(기본 `./.data/submissions`),
  제출 1건당 `<uuid>.json` 파일 1개. **git에 절대 커밋되지 않는다.**
- **보존기한 기본값: 30일.** `SAMINDANG_RETENTION_DAYS`로 바꾸거나
  `0`으로 자동삭제를 끌 수 있다 (7절).
- **서버 기동(원클릭)**: `scripts\start-clinic.bat` 더블클릭, 또는
  `npm run server` (2절).
- **태블릿 URL**: `http://<원장 PC의 LAN IP>:4173` (4절로 IP 확인).
- **원장 대시보드**: `http://localhost:4173/#doctor` (원장 PC에서).
- **직원 리셋 제스처**: 완료 화면 오른쪽 아래 구석을 2초 이상 누르고
  있는다 (9절).
- **파일럿 종료 후 데이터 전체 삭제**: `npm run purge:data` (7절, audit
  로그도 함께 삭제됨).
- **운영 audit 로그**: `.data/audit.log` — 이벤트 발생 사실만 기록,
  payload 내용은 절대 없음 (7.1a절).
- **환자 문진 화면 유휴 타임아웃**: 기본 10분, `VITE_SAMINDANG_IDLE_MINUTES`
  로 조정 (5절).

## 1. 전체 흐름

```
[환자 태블릿]                [원장 PC]
   Vite 앱          POST      node server/index.js
 (문진 작성) ───────────────▶   (:4317, LAN 내부)
                              │
                              │  GET /api/submissions (5초 폴링)
                              │  GET /api/submissions/:id
                              ▼
                         [원장 PC 브라우저]
                          DoctorView (#doctor)
```

- 문진을 마친 태블릿이 로컬 서버로 결과를 **1회 POST**한다(조회 권한 없음).
- 서버는 파일 시스템(`SAMINDANG_DATA_DIR`)에 제출 1건당 JSON 파일 1개로
  저장한다. DB도, 클라우드도, EMR 연동도 없다.
- 원장 PC의 브라우저(`#doctor` 화면)가 같은 서버에 주기적으로 물어봐서
  목록/상세를 가져온다.

## 2. 서버 기동

### 2.1 원클릭 (권장, 파일럿 운영자용)

먼저 `npm run build`로 환자 앱을 한 번 빌드해둔다(파일이 바뀔 때마다
다시 빌드). 그 다음 프로젝트 루트의 `scripts\start-clinic.bat`을
더블클릭(또는 탐색기에서 실행)한다. 이 스크립트가:

1. 핸드오프 서버(`node server/index.js`, 기본 포트 4317)를 새 콘솔
   창으로 띄운다 — 환자 제출을 받고 원장 대시보드 API를 제공한다.
2. 빌드된 환자 앱을 LAN에 서빙하는 프리뷰 서버(`npm run preview --
   host`, 기본 포트 4173)를 또 다른 새 콘솔 창으로 띄운다.
3. 콘솔에 태블릿 URL/원장 대시보드 URL/LAN IP 확인 명령을 그대로
   출력한다.

두 창을 닫거나 안에서 Ctrl+C를 누르면 그 서버가 멈춘다. 하루 끝에
그렇게 종료하면 된다(11절).

### 2.2 수동 기동

원장 PC(또는 클리닉 LAN 안의 아무 PC)에서:

```bash
npm run server
# 내부적으로: node server/index.js
```

빌드 단계가 없다 — `server/` 아래는 순수 JS라 바로 실행된다. 시작하면
콘솔에 실제 host/port/데이터 디렉터리/보존기한 설정을 출력한다.

### 2.3 환경변수

| 변수 | 기본값 | 설명 |
|---|---|---|
| `SAMINDANG_HOST` | `0.0.0.0` | 바인드 주소. LAN의 다른 기기가 접속하려면 `0.0.0.0`(전체 인터페이스)이어야 한다. |
| `SAMINDANG_PORT` | `4317` | 서버 포트. |
| `SAMINDANG_DATA_DIR` | `./.data/submissions` | 제출 JSON을 저장할 디렉터리. |
| `SAMINDANG_DOCTOR_TOKEN` | (없음) | 설정하면, loopback이 아닌 원장 요청도 이 토큰으로 허용한다. 3절 참고. |
| `SAMINDANG_ALLOWED_ORIGINS` | (빈 목록) | 원장 엔드포인트를 브라우저에서 호출할 수 있는 origin을 쉼표로 구분해 지정한다(예: `http://localhost:5173,http://192.168.0.10:4317`). `http://localhost:<포트>`/`http://127.0.0.1:<포트>`는 항상 허용되므로 일반적인 단일 PC 구성에서는 이 값을 설정할 필요가 없다. 3절 참고. |
| `SAMINDANG_RETENTION_DAYS` | `30` | 이 일수보다 오래된 제출을 서버 시작 시 1회, 이후 6시간마다 자동 삭제한다. `0`으로 설정하면 자동삭제를 완전히 끈다. 7절 참고. |

PowerShell 예시:

```powershell
$env:SAMINDANG_PORT = "4317"
$env:SAMINDANG_DATA_DIR = "C:\samindang-data\submissions"
npm run server
```

### 2.4 중복 제출(멱등성)

같은 문진 세션(payload의 `session_id`)이 네트워크 재시도, 태블릿
새로고침 등으로 두 번 이상 서버에 도착해도 레코드는 하나만 만들어진다.
서버가 처음 받은 제출은 `201`(새 레코드)로 응답하고, 이후 같은
`session_id`로 도착하는 제출은 `200`에 `duplicate: true`를 담아 **기존
레코드의 `id`/`created_at`**을 그대로 돌려준다 — 새 레코드를 만들지
않는다. 태블릿 앱은 이 두 응답을 구분하지 않고 둘 다 정상 완료 화면으로
처리한다(환자에게 오류로 보이지 않는다). 서버 콘솔 로그에는 "duplicate
submission detected" 한 줄만 남고, 제출 내용은 로그에 남지 않는다.

## 3. 보안 모델 (반드시 이해하고 운영할 것)

- **환자 엔드포인트(`POST /api/submissions`)는 쓰기 전용**이다. 태블릿은
  자기가 방금 낸 제출조차 다시 읽을 방법이 없다.
- **원장 엔드포인트**(목록/상세/상태변경/판단저장)는 다음 중 하나일 때만
  허용된다:
  1. 요청이 **loopback**(`127.0.0.1`/`::1`, 즉 서버가 돌고 있는 바로 그
     PC)에서 온다. 이것이 **진짜 보안 경계**다 — 이 서버는 원장 PC
     "위에서" 실행되는 것을 전제로 설계했다.
  2. `x-doctor-token` 헤더가 `SAMINDANG_DOCTOR_TOKEN` 환경변수 값과
     일치한다. 이 토큰은 원장이 **다른 기기**(예: 같은 진료실의 보조
     모니터/PC)에서 화면을 볼 때만 필요한 보조 수단이다.
     `SAMINDANG_DOCTOR_TOKEN`을 설정하지 않으면, loopback이 아닌 원장
     요청은 무조건 403으로 거부된다.
- **이것은 실제 인증이 아니다.** 토큰은 평문 헤더로 오가고, TLS도 없다.
  파일럿 규모(클리닉 원내 LAN, 소수 인원)에서만 안전하다고 간주한다.
  **인터넷에 절대 노출하지 말 것** — 공유기 포트포워딩, 클라우드 터널
  (ngrok 등) 사용 금지.
- **loopback만으로는 브라우저 기반 공격을 막지 못한다.** 원장 PC의
  브라우저가 (다른 탭에서) 악성 웹사이트를 열면, 그 사이트의 JavaScript가
  `fetch('http://127.0.0.1:4317/api/submissions')`를 호출할 수 있다. 이
  요청도 loopback에서 나가므로 위 1번 조건을 통과한다 — 문제는 서버가
  응답의 CORS 헤더(`access-control-allow-origin`)에 요청자의 Origin을
  그대로 반사해주면, 브라우저가 그 응답(환자 목록 등)을 악성 사이트의
  JavaScript에 넘겨준다는 점이다. 이를 막기 위해 원장 라우트는:
  1. Origin이 없는 요청(curl, 스크립트 등 브라우저가 아닌 클라이언트)은
     그대로 통과시킨다 — 브라우저는 cross-origin 요청에 항상 Origin을
     붙이므로, Origin 부재는 브라우저 공격이 아니라는 뜻이다.
  2. Origin이 `http://localhost:<포트>` 또는 `http://127.0.0.1:<포트>`이면
     허용한다 — 원장 PC 자신의 Vite 개발 서버(보통 `localhost:5173`)나
     서버 자신의 origin이 여기 해당하므로, 일반적인 단일 PC 구성은 별도
     설정 없이 그대로 동작한다.
  3. 그 외 Origin은 `SAMINDANG_ALLOWED_ORIGINS`에 정확히(대소문자
     무시) 등록돼 있지 않으면 **서버가 즉시 403으로 거부**한다(store를
     건드리기도 전에 차단 — CORS 헤더는 브라우저만 지켜주는 방어선이므로,
     서버 단에서도 한 번 더 막는다). 허용되지 않은 origin에는 절대
     `access-control-allow-origin`을 반사하거나 `*`를 쓰지 않는다.
  환자 제출(`POST /api/submissions`)은 이 규칙의 대상이 아니다 — 쓰기
  전용이고 응답에 `{id, created_at}`만 담기며, 태블릿은 LAN 내 임의의
  origin에서 접속하므로 기존처럼 origin을 그대로 반사한다.

### 3.1 정확히 누가/무엇이 이 데이터를 읽을 수 있는가 (반드시 이해할 것)

솔직하게 말하면, 이 파일럿 구성에서 저장된 문진 데이터를 읽을 수 있는
경로는 다음 세 가지뿐이며, 그 이상도 이하도 아니다:

1. **원장 PC의 파일시스템에 접근할 수 있는 사람/프로세스 전부.**
   `SAMINDANG_DATA_DIR`(기본 `.data/submissions/`) 아래 파일은 평문
   JSON이다 — 암호화돼 있지 않다. 그 PC에 로그인할 수 있거나, 그 PC의
   디스크에 접근할 수 있는 사람(원격 관리 도구, 다른 로컬 계정, 백업
   소프트웨어 등 포함)은 전부 읽을 수 있다.
2. **원장 PC 자신에서 loopback으로 서버에 접근할 수 있는 모든 프로세스.**
   3절에서 설명했듯 loopback 요청은 무조건 원장 엔드포인트를 통과한다 —
   그 PC 위에서 돌아가는 임의의 프로그램(악성 브라우저 탭의 JavaScript
   포함, Origin 가드로 그 경로는 막혀 있지만 curl류 비-브라우저 클라이언트는
   막지 않는다)이 이 조건에 해당한다.
3. **`SAMINDANG_ALLOWED_ORIGINS`에 등록됐거나 localhost인 Origin에서 접속한
   브라우저.** 그 Origin의 페이지가 실행하는 JavaScript는 무엇이든 원장
   엔드포인트를 호출할 수 있다.

**이것은 프로덕션급 인증이 아니다.** 사용자 계정이 없고, 사용자별 접근
제어가 없고, 저장 데이터 암호화(encryption at rest)가 없다. "누가
로그인했는지"를 서버가 전혀 모른다 — loopback인지, 올바른 토큰/Origin을
가졌는지만 안다.

**대신 데이터를 지키는 것**은 다음 네 가지뿐이다:

- **PC에 대한 물리적 통제** — 원장 PC를 아무나 만질 수 없는 곳에 둔다.
- **LAN 격리** — 이 서버를 인터넷에 노출하지 않는다(포트포워딩/터널 금지,
  6절의 Private 방화벽 프로필).
- **loopback 경계** — 원장 엔드포인트는 기본적으로 그 PC 자신에서 오는
  요청만 허용한다.
- **Origin 허용목록** — 브라우저 기반 크로스오리진 공격을 막는 보조 방어선.

**실제 프로덕션 배포에 필요한 것**(이 파일럿에는 없음): 사용자별 로그인과
세션 관리, 역할 기반 접근 제어(원장/직원/관리자 구분), 저장 데이터
암호화, TLS(HTTPS), 감사 가능한 인증 로그(누가 언제 로그인했는지), 그리고
정식 백업/재해복구 절차. 이 중 어느 것도 지금 구현돼 있지 않다 — 이
문서가 "안전하다"고 말하는 것은 오직 "클리닉 원내 LAN, 소수 인원, 파일럿
규모"라는 좁은 전제 안에서일 뿐이다.

## 4. 원장 PC의 LAN IP 찾기 (코드에 하드코딩하지 않는다)

`server/index.js`는 특정 IP를 알지 못한다 — `SAMINDANG_HOST=0.0.0.0`으로
모든 인터페이스에 바인드할 뿐이다. 태블릿이 접속할 실제 IP는 원장 PC에서
직접 확인한다.

Windows(원장 PC)에서:

```powershell
ipconfig | findstr /i "IPv4"
```

`무선 LAN 어댑터` 또는 `이더넷 어댑터` 아래 `192.168.x.x` 형태의 주소가
클리닉 공유기가 준 사설 IP다. (VPN이 떠 있으면 여러 개 나올 수 있으니
클리닉 Wi-Fi/유선 어댑터 것을 고른다.)

## 5. 태블릿(환자용) 빌드에 서버 주소 설정

`.env`(또는 `.env.local`, git에 커밋하지 않음)에:

```
VITE_SAMINDANG_SERVER_URL=http://192.168.0.10:4317
```

(4절에서 확인한 원장 PC의 실제 IP로 교체) 이 값을 설정하지 않으면 태블릿
앱은 오늘까지와 완전히 동일하게 동작한다 — 서버로 아무것도 보내지 않고,
전송 관련 UI도 나타나지 않는다.

선택적으로 `VITE_SAMINDANG_IDLE_MINUTES`(기본 `10`)로 문진 화면(question
phase)의 유휴 타임아웃 분을 조정할 수 있다. 만료 60초 전 "아직
계신가요?" 안내가 뜨고, 그래도 조작이 없으면 세션이 초기화되고 시작
화면으로 돌아간다(공유 태블릿에서 환자가 자리를 뜬 채 방치되는 경우를
대비한 것). 완료 화면과 원장 화면(`#doctor`)에서는 절대 동작하지 않는다.

설정 후 평소처럼 `npm run dev` / `npm run build`.

## 6. Windows 방화벽 (직접 설정해야 함 — 자동화하지 않음)

**이 프로젝트는 방화벽 규칙을 자동으로 바꾸지 않는다.** 기본적으로
Windows Defender 방화벽은 외부에서 들어오는(inbound) 임의 포트 연결을
막는다. 태블릿이 원장 PC의 4317 포트에 접속하려면, 원장 PC에서 관리자
권한으로 **Private(개인) 프로필에 한해** inbound 규칙을 열어줘야 한다.

GUI로:
1. Windows 보안 → 방화벽 및 네트워크 보호 → 고급 설정
2. 인바운드 규칙 → 새 규칙 → 포트 → TCP → 특정 로컬 포트: `4317`
3. 연결 허용 → **프로필: 개인(Private)만 체크, 도메인/공용은 해제**
4. 이름: 예) `samindang-handoff-4317`

또는 관리자 PowerShell에서 한 번에:

```powershell
New-NetFirewallRule -DisplayName "samindang-handoff-4317" `
  -Direction Inbound -Protocol TCP -LocalPort 4317 `
  -Action Allow -Profile Private
```

`-Profile Private`을 반드시 지정한다 — Public 프로필까지 열면 카페/공항
등 다른 네트워크에서도 노출될 수 있다. 클리닉 Wi-Fi가 Windows에
"공용 네트워크"로 잡혀 있다면 먼저 "개인 네트워크"로 바꾼 뒤 규칙을
적용한다.

## 7. 데이터 위치 / 보존기한(retention) / 백업 / 삭제

**환자 개인정보다 — 위치와 보존기한을 반드시 숙지하고 운영할 것.**

- **위치**: `SAMINDANG_DATA_DIR`(기본 `./.data/submissions`) 아래 제출
  1건당 `<uuid>.json` 파일 1개.
- **git에 커밋되지 않는다** — `.gitignore`에 `.data/`가 등록돼 있다.
- 서버 재시작은 데이터를 잃지 않는다 — 파일 시스템이 곧 저장소다.

### 7.1 자동 보존기한(retention) — 기본 30일

서버는 시작할 때 1번, 그 뒤로는 6시간마다 `created_at`이
`SAMINDANG_RETENTION_DAYS`(기본 **30일**)보다 오래된 제출 파일을 자동
삭제한다. 콘솔에는 삭제 **건수**만 남고 내용은 절대 남기지 않는다.

- 자동삭제를 끄려면 서버를 `SAMINDANG_RETENTION_DAYS=0`으로 실행한다.
- 보존기한을 늘리거나 줄이려면 원하는 일수를 지정한다(예:
  `SAMINDANG_RETENTION_DAYS=14`).
- 이 정리는 서버가 켜져 있는 동안에만 동작한다(스케줄러가 아니라
  프로세스 내부 타이머다) — 서버를 오래 꺼두면 그동안은 정리되지 않고,
  다음에 켤 때 한 번에 정리된다.

### 7.1a 운영 audit 로그 (누가 언제 무엇을 했는지 — 내용은 절대 아님)

`SAMINDANG_DATA_DIR`의 형제 경로(기본 구성에서는 `.data/audit.log`)에
append-only 감사 로그가 쌓인다. 한 줄 = JSON 객체 1개(JSON Lines), 정확히
아래 5개 키만 담는다:

```json
{"ts":"2025-01-01T09:00:00.000Z","event":"submission_created","submission_id":"<uuid>","actor":"patient"}
```

- `event`: `submission_created` / `submission_duplicate` / `submission_viewed`
  / `status_changed`(이때만 `status` 키 추가) / `judgment_saved`.
- `actor`: 환자용 쓰기 전용 엔드포인트에서 온 이벤트는 `patient`, 원장
  가드를 통과한 이벤트는 전부 `doctor`.
- **성함/전화번호/생년월일/약물·병력/토큰 등 어떤 payload 내용도 절대
  들어가지 않는다** — 오직 "이 id에 이 이벤트가 있었다"는 사실뿐이다.
- git에 커밋되지 않는다 — `.data/`(그리고 명시적으로 `.data/audit.log`)가
  `.gitignore`에 있다.
- `npm run purge:data`(7.4절)를 실행하면 제출 데이터와 함께 이 로그도
  통째로 삭제된다. 이 로그 자체는 아직 날짜 기준 자동 보존기한(7.1절의
  제출 데이터 retention과 달리) 정리 대상이 아니다 — 파일럿 규모(하루
  수십 건, 한 줄이 채 200바이트가 안 됨)에서는 그대로 둬도 문제되지
  않는다고 보고 미룬 부분이다.

### 7.2 백업

이 디렉터리(`SAMINDANG_DATA_DIR`)를 통째로 복사하면 된다(암호화된
외장 드라이브 권장 — 환자 개인정보 포함).

### 7.3 개별 삭제

특정 환자 데이터만 지우려면 해당 `<uuid>.json` 파일을 삭제한다. 서버가
켜져 있는 동안 삭제해도 무방하다(다음 목록 조회 시 자동으로 빠진다).

### 7.4 파일럿 종료 후 전체 삭제

```bash
npm run purge:data
```

`SAMINDANG_DATA_DIR` 아래 모든 제출을 **영구히** 삭제하는 파괴적
작업이다. 실수 방지를 위해:

- 대화형 터미널에서 실행하면 `DELETE`를 정확히 입력해야 실제로
  지운다(다른 입력은 전부 취소로 처리).
- 터미널이 없는(비대화형) 환경에서는 `--yes` 플래그 없이는 무조건
  거부한다: `node scripts/purge-data.mjs --yes`.

### 7.5 저장된 레코드의 버전 추적 / 시각 표기 규칙

저장된 제출 1건(`<uuid>.json`)은 아래 버전 필드로 "어떤 스펙/엔진/스키마
버전으로 만들어졌는지" 항상 추적 가능해야 한다:

| 필드 | 무엇의 버전인가 |
|---|---|
| `record_schema_version` | 레코드 최상위 "포장"(wrapper) 자체의 shape. 기본 `'1.0.0'`. |
| `submission.questionnaire_version` | 환자가 답한 문진 스펙(Master Spec) 버전. |
| `myungri.policy.algorithm_version` | 명리/만세력 계산 정책 버전(`src/saju/policy.ts`). |
| `myungri.engine.library_version` | 실제 계산에 쓰인 `manseryeok` 라이브러리 버전. |
| `judgment.schema_version` | 원장 판단(`ClinicianJudgment`) 데이터 계약 버전. |

**시각(timestamp) 표기 규칙**: 이 프로젝트의 모든 timestamp는 예외 없이
`new Date().toISOString()`이 만드는 ISO-8601 UTC 문자열이다(예:
`2025-01-01T09:00:00.000Z`). `created_at`/`updated_at`/`recorded_at`/
`answered_at`/audit 로그의 `ts` 모두 이 규칙을 따른다 — 로컬 시각이나
epoch 숫자를 쓰는 곳은 없다.

## 8. 태블릿이 서버에 연결되지 않을 때

1. 태블릿과 원장 PC가 **같은 Wi-Fi/네트워크**에 있는지 확인한다(게스트
   Wi-Fi는 기기간 통신을 막는 경우가 많다 — AP 격리 확인).
2. 원장 PC에서 서버가 실제로 떠 있는지 확인: 콘솔에 `listening on
   http://0.0.0.0:4317` 로그가 보이는지.
3. 원장 PC에서 `curl http://localhost:4317/api/health`(또는 브라우저로
   접속)로 로컬에서는 응답하는지 먼저 확인한다.
4. 6절의 방화벽 규칙이 적용됐는지 확인한다(Private 프로필, 올바른 포트).
5. `VITE_SAMINDANG_SERVER_URL`의 IP가 4절에서 확인한 **현재** IP와
   일치하는지 확인한다(DHCP로 IP가 바뀌었을 수 있다 — 필요하면 공유기에서
   고정 IP/예약을 설정).
6. 그래도 안 되면: 태블릿 앱은 서버 미설정 상태와 동일하게 동작하도록
   설계돼 있지 않다(전송 실패 UI가 뜬다) — 문진 내용은 화면의 개발자용
   JSON(Dev JSON)에 그대로 남아있으니 그동안 수기로 전달한다. 서버 없이도
   문진 자체는 끝까지 진행/완료된다.

## 9. 원장 대시보드 목록이 비어 있거나 오류가 뜰 때

`#doctor` 화면 데이터 소스를 "서버 제출목록"으로 바꿨는데 목록이
비어있거나 "서버에 연결할 수 없습니다" 배너가 뜨면:

1. **불러오는 중…**이 계속 떠 있으면 아직 첫 폴링(최대 5초)이 끝나지
   않은 것이다 — 잠시 기다린다.
2. **"아직 제출된 문진이 없습니다"**는 정상 빈 상태다(서버는 응답했지만
   태블릿 제출이 아직 없음). 오류가 아니다.
3. **"서버에 연결할 수 없습니다"**가 뜨면 화면의 **다시 시도** 버튼을
   누른다. 그래도 안 되면 8절의 1~4번(같은 네트워크, 서버 콘솔 로그,
   `curl .../api/health`, 방화벽)을 그대로 확인한다.
4. 신규 제출은 목록 헤더의 빨간 **"신규 N"** 배지와, 해당 행의 빨간
   테두리로 강조된다. 항목을 한 번 열면(클릭) 그 건은 `viewed`로
   바뀌어 더 이상 "신규"로 세지 않는다.
5. 데이터 소스를 "예시 데이터(fixtures)"로 바꾸면 서버 없이도 화면
   레이아웃을 항상 확인할 수 있다 — 서버 문제와 화면 문제를 구분할 때
   유용하다.

## 10. 태블릿 리셋: 다음 환자를 위한 직원 초기화 제스처

완료/대기 화면(`문진이 접수되었습니다` 등)의 **오른쪽 맨 아래 구석**에,
아무 표시도 없는 작은(약 28×28px) 터치 영역이 있다. 그 자리를
**손가락으로 2초 이상 누르고 있으면** 그 환자의 모든 응답이 즉시
지워지고 시작 화면으로 돌아간다(내부적으로 `restart()` — 응답, 진행
메타데이터, 세션 id를 전부 새로 만든다). 짧게 탭하거나 스치기만 하면
아무 일도 일어나지 않는다 — 환자가 실수로 화면 아무 데나 눌러도
초기화되지 않는다.

- 환자에게 안내하지 않는다. 문진을 마친 환자가 태블릿을 두고 나가면,
  접수처 직원이 다음 환자를 받기 전에 이 제스처로 초기화한다.
- 화면에 아무 문구/아이콘도 없다 — 의도적으로 눈에 띄지 않게 설계했다.
  직원은 화면 오른쪽 아래 구석을 누르고 있으면 된다는 것만 기억하면
  된다.
- 개발/스테이징 빌드(`devMode`)에서는 이 제스처 대신 "개발자 보기" →
  "처음 화면으로 (세션 초기화)" 버튼도 쓸 수 있다(둘 다 같은 초기화
  함수를 호출한다).

### 10.1 완료 화면 도달 시 자동으로 일어나는 일 (직원이 손대지 않아도 됨)

9절의 수동 리셋 제스처와 별개로, 앱은 완료 화면에 도달하는 즉시(전송
성공, 또는 서버 미구성으로 더 이상 전송 시도가 없음이 확정되는 순간)
아래를 자동으로 한다:

- 그 세션의 응답(`responses`)·메타데이터(`meta`)·진행 이력(`visited`)·
  시작 시각을 브라우저 메모리에서 즉시 비운다. 프로덕션 빌드에서는 개발자
  JSON 뷰어 자체가 없으므로 전송용 payload 스냅샷도 함께 비운다(dev
  빌드는 개발자가 명시적으로 확인해야 하므로 유지한다).
- 브라우저 Back(또는 태블릿 뒤로가기 제스처)이 채워진 문진 화면으로
  돌아가지 못하도록 히스토리를 잠근다 — 몇 번을 눌러도 완료 화면에
  그대로 머무른다.

즉, 9절의 2초 길게 누르기 제스처는 "다음 환자를 위해 화면을 시작
화면으로 되돌리는" 것이지, 이전 환자 응답이 화면에 남는 것을 막는 것과는
별개다 — 후자는 이미 완료 화면 진입 시점에 자동으로 처리된다.

## 11. 하루 끝 종료(shutdown)

- `scripts\start-clinic.bat`로 띄웠다면: 열린 두 콘솔 창을 각각 닫거나
  안에서 Ctrl+C를 누른다.
- 수동으로 `npm run server` / `npm run preview -- --host`를 띄웠다면
  해당 터미널에서 Ctrl+C.
- 데이터는 파일 시스템에 남아있으므로(7절) 서버를 꺼도 잃지 않는다 —
  다음 날 다시 켜면 이어서 쌓인다.
