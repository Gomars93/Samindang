# 요통 운동 단계 배정 v0.3 — 확정 규칙과 미확정 사항

> **v0.2와의 관계**: `LBP_EXERCISE_LEVEL_DRAFT_v0.2.md`는 **운동 20개가 각각
> 몇 단계인가**를 확정했다. 이 문서는 **환자가 몇 단계인가**를 정하는 규칙을
> 다룬다. 두 문서를 곱하면 "이 환자에게 줄 운동"이 나온다.
>
> **구현 상태**: `src/doctor/workspace/lbpExerciseStage.ts` (순수 함수),
> `tests/lbp-exercise-stage.spec.mjs` (189 assertions). **아직 화면에 배선되지
> 않았다** — 함수와 테스트만 있고 UI 호출부는 없다.

## 0. 이 문서가 정정하는 것

이전 세션에서 세션 진행자(Claude)가 원장께 **틀린 사실을 두 번** 보고했다.
기록해 둔다.

| 잘못된 보고 | 실제 |
|---|---|
| "ODI 0~20 → 3단계, 21~40 → 2단계" 매핑표와 운동별 권장 ODI 범위 | **어떤 원문에도 없는 창작.** Alrwaily 2016은 어떤 척도의 몇 점이 몇 단계인지 명시하지 않는다(각주 2: "use any disability measure"). 그 표는 폐기했다. |
| "통증 강도 0-10이 시스템 어디에도 없다" | **있다.** `src/spec`(태블릿)만 확인하고 내린 결론이었다. 척도는 원장 워크스페이스의 **재평가 대상(Follow-up Target)** 체계에 있다 — §2 참고. |

## 1. 결정 A — 일상생활 지장도 → 기본 단계

**입력**: `VISIT_04_SYMPTOM_IMPACT` (`payload.responses.visit_goal.chief_impact`)
— 전 증상환자 필수 문항, 급성/만성 공통.

| VISIT_04 값 | 화면 문구 | 기본 단계 |
|---|---|---|
| `severe` | 일상생활이 어려울 정도예요 | **1단계 · 증상 조절** |
| `moderate` | 많이 불편해요 | **2단계 · 움직임 조절** |
| `mild` | 조금 불편해요 | **3단계 · 기능 최적화** |
| `minimal` | 거의 지장이 없어요 | **3단계 · 기능 최적화** |

값이 없거나 위 4개가 아니면 **제안하지 않는다**(`suggestedStage: null`).
아무 단계나 찍는 것보다 "원장이 정해야 한다"고 말하는 편이 정직하다.

### 근거와 그 한계

TBC 원문의 단계 정의를 역매핑한 것이다.

| TBC 원문 | 역매핑 |
|---|---|
| Stage I — *"pain severely limits movement"* | `severe` |
| Stage II — *"moderate pain and disability"* | `moderate` |
| Stage III — *"low pain and disability"* | `mild` / `minimal` |

**원문에 "VISIT_04가 severe면 1단계"라고 적혀 있지 않다.** 이 표는 삼인당의
정책값이며 원장 승인 대상이다. 논문 근거처럼 인용하지 말 것.

### 왜 ODI를 도입하지 않았나

| 이유 | 내용 |
|---|---|
| FROZEN | ODI는 10문항 추가 = `src/spec` 수정. 이 경로는 zero-diff다. |
| 문항 적합성 | ODI 8번은 성생활 문항이다. 개원가 초진 태블릿에 놓기 어렵고, 원본 ODI도 이 항목 무응답용 분모 조정 규칙을 따로 둔다. |
| 해상도 낭비 | 최종 출력이 3단계인데 입력을 0~100% 연속척도로 받는다. |
| 용도 불일치 | ODI는 **변화 추적**(MCID 10점)용으로 검증된 도구지 **단계 배정**용이 아니다. ODI를 넣어도 "몇 점부터 2단계?"라는 질문은 그대로 남는다. |

**되돌릴 수 있는 결정이다.** 파일럿에서 VISIT_04의 `severe` 비율이 과반을
넘으면(§5 실패 모드) 이 축은 실패한 것이고, 그때 ODI 재검토가 정당해진다.

## 2. 결정 B — 점수척도는 새로 만들지 않는다 (이미 있다)

`src/doctor/workspace/finalAssessment.ts` + `lbpTargetFunction.ts`의
**재평가 대상(Follow-up Target)** 체계가 이미 척도 역할을 하고 있다.

| 구성요소 | 위치 | 내용 |
|---|---|---|
| 대상 선택 | `RevisitWorkspace.tsx:119` | LBP 목표기능 9개(걷기·앉기·서기·앉았다 일어서기·옷 입기·들기·수면·업무·기타) + 통증 강도·움직임/기능·증상 재현 3개 = 12개 중 **최대 3개** |
| 기준값 입력 | `FollowUpTargetPicker.tsx:152` | 대상마다 `baseline`(오늘) + `postTreatmentValue`(치료 직후) |
| 이전 방문값 | `PriorVisitHistoryCard.tsx:81` | 지난 방문 기준값을 오늘 입력칸 옆에 **읽기전용** 표시 |
| 재진 이어받기 | `revisitCarryForward.ts:230` | 대상 label은 이어받고 **값은 비운다**(의도적) |
| 방문 사이 자가보고 | `microFollowUp.ts:82` | 같은 대상에 환자가 직접 값 보고 |

**이 구조가 ODI보다 이 시스템에 맞는 이유**: 환자마다 재는 것이 다르다.
걷기가 문제면 "연속 5분", 앉기면 "20분", 들기면 "5kg". ODI는 모든 환자에게
같은 10문항을 묻지만 이 구조는 **그 환자의 그 동작**을 잰다(PSFS의 구조).

**타입은 `string`(자유 텍스트)이다.** 숫자를 강제하지 않는다 — 주석에
"free-text-or-scale shape"로 명시되어 있다.

## 3. 결정 C — 통합판단은 "원장 주도형"으로 한다

원장 선택은 **통합판단**이었다. 그런데 이 저장소에는 정면으로 걸리는
아키텍처 원칙이 있다.

```typescript
// finalAssessment.ts:123
export const REPEAT_VISIT_AUTO_COMPARE_STATUS =
  '재진 자동 비교: 자동 판단 없음 — 이전 방문 기록은 아래에서 원장이 직접 확인'
```

`FollowUpTarget`의 주석도 같은 말을 한다: *"never an auto-computed number,
never an inferred improvement/worsening judgment"*. `rehabSuggestion.ts`,
`lbpWorkingHypothesis.ts`, `lbpExerciseRecommendation.ts`도 전부 "no numeric
score, no threshold, no ranking"으로 통일되어 있다 — 우연이 아니라 관통하는
설계 원칙이다.

그래서 통합판단을 두 가지로 갈랐다.

| 안 | 내용 | 원칙 위반 | 채택 |
|---|---|---|---|
| **C-1 원장 주도형** | 시스템이 재료를 모아 **제안 단계 + 근거 문장**을 띄우고, 확정은 원장이 누른다 | 없음 | **채택** |
| C-2 자동 계산형 | `baseline`을 숫자로 바꾸고 델타를 계산해 단계를 자동 상향 | `REPEAT_VISIT_AUTO_COMPARE_STATUS` 폐기 필요 | 보류 |

**C-1을 고른 이유는 원칙 때문이 아니라 실무 때문이다.** 지금 자동 상향 규칙을
만들면 그 규칙이 맞는지 검증할 데이터가 0건이다. 파일럿에서 원장이 실제로
무엇을 보고 단계를 올리는지 관찰한 뒤에 C-2로 승격하는 것이 순서다.

### 통합판단에 들어가는 재료

기본 단계(§1)에 더해, 아래 두 조건이 **단계를 낮춘다**(올리지는 않는다).

| 조건 | 출처 | 효과 | 근거 |
|---|---|---|---|
| 발병 1주 이내 | `VISIT_03 = within_1w` | 최대 **2단계**까지 | TBC Stage I은 "recent onset"에 더해 증상이 두드러질 것을 함께 요구한다. "1주 이내"만으로 1단계까지 내리면 급성 초진 전원이 VISIT_04와 무관하게 1단계가 되어 일상지장도 축 자체가 무의미해진다. 급성기에 3단계(부하)로 바로 가는 것만 막는다. |
| 움직임 두려움 큼 | `LBP_13 = YES` | 최대 **2단계**까지 | 회피가 남은 상태에서 기능 최적화로 올리는 것은 이르다. 다만 1단계까지 내릴 근거는 없다. |

아래 세 가지는 **단계를 바꾸지 않고 근거 문장으로만 표시**한다. 이 값들로
단계를 움직일 근거가 원문에 없기 때문이다.

- `LBP_12` 회복 기대 (0~10)
- `LBP_13 = SOMEWHAT` (두려움 조금)
- `LBP_14` 일·집안일 지장 (`MAJOR` / `SOME`)

### 재진에서도 "오늘의 답변만" 본다

이 함수는 이전 방문의 `baseline`을 읽지 않는다. 자유 텍스트라 파싱할 수 없고,
파싱하는 순간 위 원칙을 어긴다. 이전 방문값은 기존 `PriorVisitHistoryCard`가
지금처럼 읽기전용으로 옆에 띄우고, **비교는 원장이 눈으로 한다.**

테스트가 이 제약을 소스 텍스트로 강제한다 —
`tests/lbp-exercise-stage.spec.mjs` §11.

## 4. 전체 흐름

```
[초진]
  VISIT_04 일상지장도 ─┐
  VISIT_03 발병시기   ─┼─→ 제안 단계 + 근거 문장 ─→ 원장이 확정
  LBP_12/13/14        ─┘    (1 / 2 / 3 / 판단보류)
                                    ↓
  원장이 목표기능 선택 (걷기·앉기·들기…)   ← 이미 있음(lbpTargetFunction.ts)
                                    ↓
  (확정단계 × 목표기능) → 운동 3~5개        ← v0.2 표
                                    ↓
  재평가 대상 baseline 기록                ← 이미 있음(FollowUpTargetPicker)

[재진]
  이전 baseline 표시(자동판단 없음) + 오늘 문진 → 제안 + 근거 → 원장 확정
```

## 5. 파일럿에서 가장 먼저 볼 숫자 — 실패 모드

**`VISIT_04`의 실제 분포.** 초진 환자는 아파서 오므로 `severe`/`moderate`에
쏠릴 수 있다. 쏠리면 전원 1~2단계로 배정되어 이 축이 무의미해진다.

- `severe`가 60%를 넘으면 → 이 축은 실패. ODI 재검토가 정당해진다.
- `minimal`과 `mild`가 실질 구분이 안 되면(둘 다 3단계로 같은 취급이라 당장은
  무해하지만) → 4단계가 아니라 3단계 문항으로 봐야 한다.

## 6. 아직 안 정한 것

1. **단계 확정 UI를 어디에 놓을 것인가** — PainWorkspace의 어느 위치, 어떤
   컴포넌트. 아직 배선 안 됨.
2. **`LBP_07` 재발(recurrence)을 cap에 넣을 것인가** — TBC Stage I은 "recent
   onset **or recurrence**"라고 쓴다. 지금은 넣지 않았다(규칙 창작을
   최소화). 넣으려면 원장 판단이 필요하다.
3. **급성 환자의 공포회피** — `LBP_13`은 3개월 이상 환자만 답한다. 급성기
   회피가 만성화의 강한 예측인자인데 태블릿에 안 잡힌다. 메우려면 `src/spec`
   수정이 필요하므로 지금은 원장 관찰로 남긴다.
4. **C-2(자동 계산형) 승격 시점** — 파일럿 데이터가 쌓인 뒤 재검토.
5. **준비조건 15개 중 진짜 안전 금기** — v0.1 §C에서 제기했고 여전히 미결.
   대부분은 자세 수행 가능 여부이고, 실제 안전 내용은 이미 각 운동의
   `stopReviewKo`에 있다.
