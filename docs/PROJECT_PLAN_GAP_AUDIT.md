# 삼인당 태블릿·명리 진료 시스템 — 기획 누락 점검

## 기존 기획에서 반드시 유지할 핵심
1. 굿닥은 범용 접수 frontend, 삼인당 정밀문진·명리 시스템은 독립 웹앱.
2. 환자 입력 → deterministic 만세력/사주 계산 → 구조화된 문진 요약 → 박경남 원장 최종 판단.
3. LLM이 인터넷 명리 지식을 섞어 독자적으로 임상 규칙을 창작하거나 자동처방하지 않음.
4. 출생정보는 생년월일·성별·양/음력·12시진/모름을 핵심으로 함.
5. 명리와 임상진찰이 충돌할 때의 우선순위는 박경남 원장의 실제 규칙을 추출해 확정.
6. 원장 설명은 선천 특징 최대 3개 → 현재 증상 연결 최대 2개 → 치료 우선순위/한약 방향 → 질문 순으로 15~20분 내 표준화.
7. 진료 후 1분 복기 4문항과 `★ 학습 케이스`를 향후 규칙집/Shadow Mode의 학습자료로 축적.
8. 연구용 추가질문을 환자에게 억지로 넣지 않고, 진료에 필요한 데이터에 timestamp/version을 남김.

## 현재 자동주행 계획에서 발견한 누락/보완점

### A. 명리 계산 pipeline이 빠져 있었음 — 반드시 추가
- 단순 생년정보 저장이 아니라 deterministic 계산 모듈이 필요.
- 계산 원본값과 정규화값, 계산 버전을 분리 저장.
- 야자시/조자시·진태양시 등은 임의 결정하지 않고 pending policy로 관리.

### B. 음력 윤달 ambiguity
- 음력 입력에서 윤달 여부가 필요한 경우를 무시하면 날짜 변환이 틀릴 수 있음.
- 시스템은 추측하지 않고 yes/no/unknown 또는 unresolved 처리해야 함.
- 이는 기존 기획의 '윤달/출생시간 세부규칙 협의'를 구현 단계에서 명시적으로 다루기 위한 보완사항.

### C. '원장에게 보여주기'만 있고 '원장 판단을 구조화해 남기기'가 빠져 있었음
- 핵심 선천 특징 3개, 현재 증상 연결 2개, 사주만 본 예상, 실제 진찰 후 수정, 최종 치료축, 처방 방향, 학습 케이스를 구조화해야 함.
- 이 데이터가 없으면 향후 Rule Engine/Shadow Mode를 만들 근거가 축적되지 않음.

### D. 계산 결과와 임상 판단의 provenance/version
- 환자 raw input / deterministic calculation / clinician interpretation / 향후 AI rule candidate를 한 덩어리로 저장하면 안 됨.
- 각각 별도 layer와 version/timestamp가 필요.

### E. 공유 태블릿 개인정보 종료처리
- 기존 기획에는 완료 후 개인정보 화면 초기화/자동 로그아웃이 있음.
- 현재 구현 큐에는 명확하지 않았으므로 별도 hardening task로 추가.
- 뒤로가기, inactivity, 다음 환자 시작 시 이전 환자 정보가 남지 않는지 검증 필요.

### F. 환자 대기상태 화면
- 기존 기획의 '접수 완료 → 상세문진 → 체질분석 준비 중 → 원장님 진료' 흐름이 빠져 있었음.
- 직원의 반복 안내를 줄이는 운영 기능이라 자동화 범위에 포함하는 것이 타당.

### G. 박경남 원장 암묵지 추출 기반
- 실제 녹음·전사는 개인정보/동의 정책이 필요하므로 자동으로 켜면 안 됨.
- 대신 지금 할 수 있는 것은 1분 복기 UI/데이터 구조와 학습 케이스 표시까지.
- 실제 녹음 동의, 보관기간, 원음삭제, 접근권한은 사람 결정이 필요한 gate로 남김.

## 의도적으로 아직 자동구현하지 않을 것
1. 굿닥/동의보감 실제 write-back: 업체/API/운영 권한 확인 필요.
2. 예약 전 외부 링크 사전입력: 인터넷 공개 배포·인증·보안 설계가 필요.
3. 야자시/조자시·진태양시 최종 규칙: 박경남 원장 임상정책 결정 필요.
4. AI Rule Engine: 실제 박경남 원장 승인 규칙이 축적되기 전에는 만들지 않음.
5. 항상 켜진 진료 녹음: 기존 기획에서도 제외.
6. AI 자동처방/사주 기반 질병 확정: 금지.
7. 환자용 개인화 명리 리포트: Phase 2 이후, 규칙 검증 후.
